# BlockIT benchmark report (1.9)

Before/after comparison of the BlockIT scan engines on the same machine, same
trees, alternating paired runs. Read with `docs/PERFORMANCE-ANALYSIS.md` (why the
numbers move) and `docs/PR-fast-scan.md` (review notes). Raw results:
`docs/benchmark-1.9.json`.

## Machine and build

| | |
|---|---|
| CPU | AMD Ryzen 7 7435HS, 16 logical cores |
| Memory | 23.7 GB |
| OS | Windows 10.0.26200 (win32 x64) |
| Runtime | Node v22.21.1 under Electron |
| Storage | NVMe SSD (fixtures and the real tree on the same volume) |
| "before" engine | archived v1.5.0 worker, the code on `main` (`D:\Projects\BlockIT\.bench\main15\worker\scanner-worker.js`) |
| "after" engine | 1.9 worker, this branch (`D:\Projects\BlockIT\dist-electron\scanner-worker.js`) |
| Command | `cross-env ELECTRON_RUN_AS_NODE=1 electron scripts/bench-scan.cjs suite` |

Both engines ran as the same (elevated) user, alternating, warm filesystem cache,
with worker startup, native-helper startup, index build and the SQLite checkpoint
included in the wall time. Each profile is the median of its trials, and every
paired run is checked for output parity.

## Results

| Profile | v1.5 (before) | 1.9 (after) | Speedup | Output parity |
|---|---:|---:|---:|---|
| generated small | 1,683 ms | 588 ms | **2.86x** | exact (tree hash, totals, aggregates) |
| generated medium | 9,806 ms | 1,076 ms | **9.11x** | exact |
| generated large/deep | 24.3 s | 2,030 ms | **11.95x** | exact |
| real-world `D:\Projects` | 206.9 s | 6,633 ms | **31.19x** | explained difference, see below |

Speedup grows with tree size because small scans are dominated by fixed process
and helper startup time.

### Parity on the generated profiles

For all three generated profiles both engines produce identical results: equal
node, file, folder and link counts, equal total bytes, equal root roll-ups, equal
category and extension aggregates, and an equal SHA-256 digest over every row's
path, kind, size and parent path. The harness exits non-zero on any difference.
The same run failed as expected while the volume dispatch bug was still present.

### The real tree, and the four rows that differ

`D:\Projects` is live, so parity is asserted by scanning it with the new engine
twice and the old engine once, then diffing rows. The control comparison (new
against new) reported **0 differing rows**, so the tree was quiet during the run;
the old engine's two runs agreed with each other as well. The engines differ on
exactly four rows:

| Path | v1.5 | 1.9 |
|---|---|---|
| `D:\Projects\BlockIT\release\win-unpacked\resources\app.asar` | folder, size 0, warning `ENOTDIR` | file, 31,271,257 bytes |
| `D:\Projects\BlockIT\node_modules\electron\dist\resources\default_app.asar` | folder, size 0, warning `ENOTDIR` | file, 109,371 bytes |
| `D:\Projects\Adz\companion\node_modules\electron\dist\resources\default_app.asar` | folder, size 0, warning `ENOTDIR` | file, 108,953 bytes |
| `D:\Projects\Adz\companion\dist\ADZ-companion\resources\default_app.asar` | folder, size 0, warning `ENOTDIR` | file, 108,953 bytes |

Electron's `fs` reports `.asar` archives as directories, so the v1.5 engine
created folder rows, tried to open them, and failed with `ENOTDIR` (these were its
four warnings). The native engine reads the Win32 enumeration attributes, where an
`.asar` file is a file, and records its real size. The new engine is therefore
more accurate here, and the difference is systematic rather than tree drift. Every
other row matched.

## Whole-drive MFT mode

Whole-drive scans read the NTFS Master File Table directly and need administrator
rights. This is the mode the dispatch bug affected. With the fix, a full `C:\`
scan completed:

| | |
|---|---|
| Engine | `volume` (MFT volume mode) |
| Wall time | 79.8 s (previously truncated after 4,096 entries) |
| Nodes | 2,827,104 |
| Files | 2,474,269 |
| Folders | 352,292 |
| Bytes | 148,675,457,968 |
| Warnings | 0 |
| Totals check | `run.file_count` and `run.total_size` equal the node-table sums (`npm run test:drive`) |

For reference, the archived v1.7 directory-walk baseline for the same volume was
1,779.5 s median (`docs/verification-1.8.md`, `docs/scanner-comparison-1.8.json`).
The gap between a full MFT pass and a full directory walk is the headline of this
engine line; the 1.9 work is what makes the MFT pass usable.

## Reproducing

```powershell
npm run build
npm run bench:scan suite          # writes docs/benchmark-1.9.json
npm run test:drive                # elevated whole-drive totals check
```

The "before" worker is the current `main` engine. Rebuild it into
`.bench/main15/worker/scanner-worker.js` with:

```powershell
git worktree add .bench/main15 main
npx tsup .bench/main15/electron/scanner-worker.ts --format cjs --platform node --target node20 --out-dir .bench/main15/worker --external electron --external better-sqlite3
```

Environment overrides: `BEFORE_WORKER`, `AFTER_WORKER`, `HELPER`, `REAL_TREE`,
`TRIALS`, `OUT`, `BENCH_FIXTURES`.

## Limits

- Warm-cache local NTFS only; cold cache, HDD, network and removable media are not
  covered.
- CPU and RSS style figures elsewhere describe the Electron test host only and
  exclude the native helper process.
- The real-tree profile reflects one machine at one moment. The generated profiles
  are the reproducible ones; a frozen copy of a large tree is the way to make the
  real-tree profile perfectly repeatable.
